Understanding the exercise scenario¶

In a large variety of business processes, forms (like an order form) require filling a large number of fields in the UI. In data reality, some fields are often left blank when an order is created — for example, the shipping point, payment terms, or plant. Filling these in correctly requires experience and takes time.

In this exercise, you will build a neural network machine learning model using algorithms from the Predictive Analysis Library (PAL) in SAP HANA Cloud, to predict values to autocomplete 8 fields in a Sales Order form. The PAL multi-target MLP algorithm in its latest release (2026 Q3), it also allows to handle columns (fields), which are sometimes already filled and sometimes have to predicted, thus have a dual role. Again, in reality a common pattern too.

In this exercise you will

  • Access and explore the Sales Order Data
  • Fine-tune a pre-trained model with new Sales Order data
  • Apply the model to predict and autocomplete new Sales Order cases
  • Measure and review the prediction accuray

Ex. 3.1 - Access and explore the Sales Order Data¶

As Sales Order demo data, we are using the SALT: Sales Autocompletion Linked Business Tables Dataset the benchmarking dataset, which was released by the SAP RPT team and is based on the SAP sales-order autocompletion (SOAC) use case. The SAP/SALT · Datasets at Hugging Face has about ~29 columns and roughly 1.9M rows for training and 400k rows of test data.

The dataset contains typical SAP sales orders. Each order has 27 fields split into two groups:

  • 19 input fields — these are always known when an order is created .
    • for example: which product, which customer (sold-to party), which country (billing country/region), which sales org
  • 8 target fields — these are sometimes left blank and need to be predicted,
    • for example: which plant, which shipping point, what payment terms, which sales office, which incoterms, which shipping condition

The following datasets have be pre-loaded to the SAP HANA Cloud instance, schema DA262_SHARED

  • A pre-trained MT_MLP model (trained on 1.9 million Sales Order training data rows) in table SOAC_PRETRAINED_MODEL
  • Sales order test data sets SOAC_TESTDATA (402k rows) and SOAC_TESTDATA_SUBSET (1000 rows)
    • Sales Order rows, the model it has never seen during training, this is how we measure how well the model generalizes to unseen data based on patterns it learned during training.

Ex. 3.2 - Train a multi-target classification model for sales order form autocompletion¶

We seek to build a multi-target classification model for this use cases, based on the Multi-Task MLP algorithm, from the SAP HANA Cloud Predictive Analysis Library (PAL)
Let's first understand What is a Multi-Task MLP?

  • MLP (Multi-Layer Perceptron) is a type of neural network.
  • “Multi-Task” means the model allows to predicts multiple target columns in a single model, all 8 missing fields in one pass — instead of running 8 separate models. This is faster and lets the fields help each other.
  • In it's 2026 Q3 release, the algorithm also __allows to handle columns (fields) with a dual role, columns which are sometimes already filled and can be treated as a feature value and sometimes are empty and have to predicted.

The model you just loaded learned from 1.9 million past sales orders. But the real world keeps changing — new customers, new products, new routes. Fine-tuning lets the model learn new patterns without forgetting what it already knows.

Simple analogy: A salesperson with 10 years of experience gets 1,000 orders from a brand-new market. They learn the new patterns on top of their experience — not instead of it.

Review the Model Training Parameters used

The code in the next step uses the exact same settings that were used to train the 1.9M model.

  • The only difference is one new parameter added for fine-tuning: finetune=True.
  • The parameter ENABLE_STREAMING=1 is also new with 2026 Q3 version of the algorithm, allowing for much more efficient way of processing the categorial column data, being faster and consuming much fiewer memory resources.

Neural network shape:

Parameter Value What it means
network_type resnet Type of neural network — good at learning complex patterns
embedded_num 32 Each category gets a list of 32 numbers to represent it
residual_num 4 4 deep layers stacked inside the network

Training settings:

Parameter Value What it means
num_epochs 100 Do at most 100 training rounds
batch_size 256 Look at 256 orders at a time
learning_rate 0.01 How big a step to take when updating the model
training_percentage 0.9 Use 90% for training, 10% to check progress
early_stop True Stop automatically when the model stops improving
save_best_model True Keep the best version found during training
random_state 42 Fixed starting point — results are the same every time
training_style stochastic Mini-batch training — same method as the 1.9M training
ENABLE_STREAMING 1 Process data in chunks — same method as the 1.9M training

New for fine-tuning:

Parameter Value What it means
⭐ finetune True Load the 1.9M knowledge first — do NOT start from zero

Why is finetune=True the most important parameter? Without it the model ignores everything it learned from 1.9M orders and starts fresh. That is called catastrophic forgetting — the model only knows the 1,000 new orders. With finetune=True it builds on top of 1.9M knowledge instead of replacing it.

Around 0.18 ✅ Good — model started from the 1.9M knowledge
Around 0.80 ❌ Bad — model started from zero

Ex. 3.5 - Improve prediction latency with stateful models (OPTIONAL)¶

We have confirmed the model is accurate. Now we look at how to make it production-ready.

The problem with standard predict: Every time you call clf.predict() (clf is the model object we created in section 3.3), HANA loads the full model from disk into memory, runs the prediction, then discards the model from memory. For a model with 14,864 rows of weights, this disk-load step takes hundreds of milliseconds — too slow for real-time order processing.

The solution — Stateful Predict: Load the model into HANA server memory once, keep it there, and reuse it for every prediction. The model stays in memory between calls, so each prediction only does the actual computation — no disk loading.

In this section we prove two things with real numbers:

  1. Accuracy — stateful predict gives exactly the same results as standard predict
  2. Speed — stateful predict is significantly faster per order

Step 8: Load the Model into HANA Server Memory¶

Before using stateful predict, we load the model's learned numbers (called weights) into HANA server memory once using create_model_state(). Weights are simply the values the model adjusted during training to make accurate predictions — think of them as the model's "memory" of 1.9 million past orders.

Think of it like opening a large file — the first open takes time, but once it is open you can read from it instantly as many times as you want.

create_model_state() returns a State ID — a unique reference to the model that is now sitting in memory. In the next steps we pass this State ID to the prediction call instead of the model table, which tells HANA: "the model is already in memory — use it directly."

Confidence Scores: Can We Trust the Model?¶

Along with each prediction, the model outputs a confidence score between 0 and 1 — how sure it is about that answer.

A trustworthy model behaves like this:

  • When it gets the answer right (rank 1) → confidence is high (close to 1.0)
  • When it is less certain and the correct answer slips to rank 2 or 3 → confidence is low

The table below shows the average confidence split into these two groups. A large gap between the two columns means the model knows when it knows — you can use the confidence score in production to decide when to auto-fill the field and when to ask the user to confirm.

# ── Accuracy helper ───────────────────────────────────────────────────────────
# truth_union converts the wide test table (one column per field) into the same
# long format as predictions (one row per field) so they can be joined on (ID, TARGET).
truth_union = "\n    UNION ALL ".join(
    f'SELECT "ID", \'{col}\' AS TARGET, CAST("{col}" AS NVARCHAR(1000)) AS TRUE_VAL'
    f' FROM "{DATA_SCHEMA}"."{TEST_TABLE_SMALL}"'
    for col in ALL_TARGETS
)

_field_order = " ".join(
    f"WHEN '{col}' THEN {i+1}"
    for i, col in enumerate(ALL_TARGETS)
)


def compute_accuracy(result_table):
    """Compute Top-1 %, Top-3 %, and MRR for each predicted field.

    Parameters
    ----------
    result_table : str
        HANA table name — must have columns: ID, TARGET, SCORE, CONFIDENCE.

    Returns
    -------
    pd.DataFrame  columns: Field | Top-1 | Top-3 | MRR
    """
    sql = f"""
WITH
-- Rank every candidate prediction best-first for each (order, field) pair.
RANKED AS (
    SELECT "ID", "TARGET", "SCORE",
           ROW_NUMBER() OVER (PARTITION BY "ID", "TARGET" ORDER BY "CONFIDENCE" DESC) AS RNK
    FROM "{result_table}"
),
-- Convert the wide test table to long format: one row per (order, field).
TRUTH AS (
    {truth_union}
),
-- Find what rank the true answer received.
-- TRUE_RANK = 1 → first guess correct (Top-1 hit)
-- TRUE_RANK ≤ 3 → correct in top 3    (Top-3 hit)
-- TRUE_RANK NULL → correct answer not in any candidate
TRUE_RANKS AS (
    SELECT t.ID, t.TARGET,
           MIN(CASE WHEN r."SCORE" = t.TRUE_VAL THEN r.RNK END) AS TRUE_RANK
    FROM TRUTH t
    LEFT JOIN RANKED r ON r."ID" = t.ID AND r."TARGET" = t.TARGET
    GROUP BY t.ID, t.TARGET
)
SELECT TARGET AS "Field",
    ROUND(SUM(CASE WHEN TRUE_RANK = 1  THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 1) AS "Top-1",
    ROUND(SUM(CASE WHEN TRUE_RANK <= 3 THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 1) AS "Top-3",
    ROUND(SUM(CASE WHEN TRUE_RANK IS NOT NULL THEN 1.0 / TRUE_RANK ELSE 0.0 END) / COUNT(*), 3) AS "MRR"
FROM TRUE_RANKS
GROUP BY TARGET
ORDER BY CASE TARGET {_field_order} END
"""
    return myconn.sql(sql).collect()
